# Teams → Bitrix24: сервис обработки лидов с выставки

Сервис слушает канал Microsoft Teams, распознаёт в потоке смешанных
сообщений (текст, фото визиток, голосовые) отдельные контакты, извлекает и
проверяет структурированные поля лида и заводит/обновляет карточку лида в
Bitrix24 без ручных шагов.

> Этот README и `DECISIONS.md` добавлены при проверке проекта — в присланном
> архиве не было ни README, ни `.env.example`, ни каталогов `templates/` и
> `static/`, необходимых `web_app.py` для запуска. Список конкретных правок
> кода — в конце этого файла и в комментариях `ДОБАВЛЕНО:` / `ИСПРАВЛЕНО:`
> прямо в коде.

## Архитектура

```
poller.py            — опрашивает канал Teams (Graph API), пишет сообщения в SQLite
worker.py            — скачивает вложения (фото визиток, голосовые) из Graph
content_worker.py    — OCR визиток (EasyOCR) + транскрибация голоса (faster-whisper)
grouping_worker.py   — группирует сообщения в лиды: "один контакт = один лид"
extraction_worker.py — извлекает поля лида (OpenAI structured output) с проверкой evidence
bitrix_worker.py     — создаёт/обновляет лид в Bitrix24, ищет дубли, шлёт подтверждение в Teams
web_app.py           — веб-интерфейс (FastAPI): список лидов, карточка, повторная отправка, админка
run_service.py       — supervisor: проверяет .env и поднимает все воркеры одним процессом-родителем
```

Все воркеры общаются только через одну SQLite-базу (`data/messages.db`,
режим WAL) — она же durable-очередь заданий (таблицы `processing_jobs`,
`crm_sync_state` с `attempts`/`next_attempt_at`/backoff). Внешнего брокера
очередей нет: для нагрузки "200–400 лидов за 3 дня" одного файла SQLite с
WAL достаточно, и это резко упрощает эксплуатацию.

Подробные инженерные решения (в т.ч. ответы на раздел 5 ТЗ) — в
[`DECISIONS.md`](./DECISIONS.md).

## Сквозной прогон

```bash
python3 run_service.py
```

поднимет все шесть воркеров одним процессом-супервизором (перезапускает
упавший воркер через 3 секунды) и напечатает `SERVICE_CHECK_OK`.

Веб-интерфейс запускается отдельно (у него другой рантайм — ASGI):

```bash
uvicorn web_app:app --host 0.0.0.0 --port 8000
```

Откройте `http://localhost:8000`, войдите под `DASHBOARD_ADMIN_USER` /
`DASHBOARD_ADMIN_PASSWORD` (Basic Auth).

Проверка "вручную": напишите в тестовый канал текст с email/телефоном
("Познакомился с Ивановым, ООО Ромашка, +7 999 000-00-00, ivanov@romashka.ru,
просил перезвонить") — через `POLL_INTERVAL_SECONDS` + `GROUP_DEBOUNCE_SECONDS`
секунд лид должен появиться на `/`, а в канал — прийти подтверждение с ID
карточки в Bitrix24.

Отдельные шаги можно прогнать по одному разу без ожидания опроса:

```bash
python3 grouping_worker.py --once
python3 extraction_worker.py --once
python3 bitrix_worker.py --once          # --dry-run — посчитать, что было бы отправлено, без записи в Bitrix
```

## Эталонный набор и метрики (раздел 1.4 / 7 ТЗ)

Генератор синтетического эталонного набора (~60 сообщений, ~20–25 лидов, все
сценарии 1.1–1.3 включая "один посетитель — два менеджера") в этой версии
**не реализован** — это отдельная задача (нужно воспроизвести в тестовом
канале Teams голосовые и фото визиток, а не только текст). Как это сделать и
как посчитать метрики после генерации:

1. Разметить эталон вручную: для каждого реального сообщения в тестовом
   канале — ожидаемый `lead_group_id` (или "не лид") и ожидаемые поля лида.
2. Прогнать пайплайн (`run_service.py`, дождаться `content_ready` →
   `lead_groups` → `crm_sync_state.status = synced` по всем сообщениям).
3. Сравнить с разметкой: `SELECT` по `grouping_results`/`lead_extractions`/
   `crm_sync_state` даёт готовый материал для precision/recall по
   группировке (совпадение `lead_group_id` с эталонной группой) и по каждому
   извлечённому полю (точное совпадение / пусто-когда-должно-быть-пусто).
4. Идемпотентность (обязательный результат раздела 2) проверяется без
   разметки: повторный `python3 bitrix_worker.py --once` на уже
   синхронизированных лидах должен вернуть `processed=0` новых `crm.lead.add`
   (см. `crm_sync_state.status='synced'` + `synced_revision >= revision`
   guard в `process_candidate()`), а рестарт мидпроцесса — что
   `recover_interrupted_jobs()`/`needs_reextract` не создают дублей.

## Известные ограничения / что осознанно отложено

* Контакт и компания как отдельные сущности CRM (п. 3.4, "дополнительно") —
  не реализовано, лид создаётся с текстовыми `COMPANY_TITLE`/`NAME`. Bitrix
  сам создаёт связанную компанию/контакт из этих полей при конверсии лида,
  что для потока "выставка → лид → менеджер разбирает" покрывает
  большинство случаев дешевле, чем `crm.contact.add`/`crm.company.add` с
  отдельной дедупликацией.
* Прикрепление фото визитки к карточке лида через `disk.folder.uploadfile`
  (п. 3.4, "дополнительно") — не реализовано. Фото уже сохранено локально и
  доступно из карточки лида в веб-интерфейсе (раздел 4.1, "доступ к исходным
  сообщениям"); прикрепление именно в Bitrix — дополнительный вызов, который
  стоит делать пакетно вместе с `crm.lead.add`, если он понадобится.
* Автоматическое построение справочника `employee_mappings` из
  `user.get` Bitrix (сопоставление по email/имени) — не реализовано;
  сопоставление "автор Teams → сотрудник Bitrix" администратор задаёт вручную
  на странице `/admin` (ID автора Teams виден там же в списке
  "Авторы без сопоставления"). Это сознательный компромисс: имена в Teams и
  Bitrix не гарантированно совпадают, а неверное автосопоставление
  ответственного стоит дороже (лид уходит не тому менеджеру), чем разовая
  ручная настройка на 5–15 сотрудников отдела продаж.

## Разбор боевого прогона 21.09 (вторая итерация правок)

По логам реального прогона в тестовом канале нашлись и исправлены ещё четыре
дефекта — все подтверждены тестами на воспроизведённом сценарии:

* **Фото визитки никогда не скачивалось.** Картинка, вставленная в сообщение
  Teams (а не приложенная файлом), лежит не в `attachments`, а в
  `hostedContents`, со ссылкой `https://graph.microsoft.com/.../hostedContents/
  .../$value` внутри `<img src=...>` в теле сообщения. `worker.py` смотрел
  только в `attachments`, поэтому файла не было → не было OCR → сообщение
  доходило до группировки пустым и списывалось как `empty_content`. Теперь
  такие картинки распознаются, скачиваются по прямой Graph-ссылке (её нельзя
  оборачивать в sharing-токен) и проходят OCR.
* **Комментарий лида собирался только из голосовых.** ТЗ п. 3.1 требует
  «Полный ввод менеджера: набранный текст + дословная расшифровка голоса», а в
  `COMMENTS` попадали только расшифровки. Для контакта без единого голосового
  комментарий уходил в Bitrix пустым. Теперь собирается полный ввод в
  хронологическом порядке, включая отметку о сообщении-вложении без подписи.
* **Короткие приписки терялись.** «Проект игры», «И пн встреча» не содержат
  ни реквизитов, ни ключевых слов, поэтому получали `NON_LEAD` ещё до того,
  как проверялось, не дополняют ли они уже открытый контакт того же менеджера.
  Теперь такая приписка присоединяется к контакту (окно
  `FOLLOW_UP_WINDOW_SECONDS`), если она не выглядит организационной и не
  вводит нового человека («подошёл…», «встретил…» — такие случаи по-прежнему
  решает LLM, а не правило).
* **Собственные карточки сервиса возвращались в обработку.** Подтверждение
  «Лид передан в Bitrix24» приходило обратно через поллер как обычное
  сообщение: маркер `[LEADBOT]` в карточку не подставлялся, а искался только
  в теле сообщения, которого у адаптивной карточки нет. Теперь карточка
  помечает себя маркером, маркер ищется во всём сообщении, а сообщения от
  приложений игнорируются по умолчанию (`IGNORE_APPLICATION_MESSAGES`).

Также добавлена страница **«Без лида»** (`/unassigned`): сообщения, которые
сервис намеренно не отнёс ни к одному контакту (в т.ч. `AMBIGUOUS`, когда
приписка могла относиться к двум открытым контактам сразу), больше не
исчезают — их видно списком и можно вручную присоединить к нужному лиду.
Лид после этого переизвлекается и **обновляется** в Bitrix24, второй лид не
создаётся.

> Важно про уже обработанные сообщения: исправления применяются к тем
> сообщениям, которые проходят пайплайн заново. Для сообщений, уже
> разобранных старым кодом, выполните `python grouping_worker.py --rebuild
> --once` (удаляет только производные `grouping_results`/`lead_groups`;
> сами сообщения, скачанные файлы, OCR и расшифровки сохраняются). Стабильные
> `group_key`/`crm_external_key` теперь сохраняются в `group_key_registry`,
> поэтому пересборка обновляет прежний лид, а не создаёт новый. После этого
> перезапустите сервис.

## «Один контакт = один лид из нескольких сообщений» — это уже автоматика

Важное уточнение по поводу страницы «Без лида»: это **не** основной механизм
сборки контакта из нескольких сообщений, а страховочная сетка для редких
действительно неоднозначных случаев. Основной механизм — полностью
автоматический и не требует ручных шагов, как и требует ТЗ (раздел 2):

1. **Детерминированные правила** в `grouping_worker.py`
   (`deterministic_decision()`) — ответ в треде, точное совпадение
   email/телефона, языковые маркеры продолжения/нового контакта, приписка без
   реквизитов рядом по времени и т.д. Они покрывают подавляющее большинство
   сообщений и решают мгновенно, без обращения к модели.
2. **LLM-фолбэк** (`llm_decide()`) — только для того, что не покрыли правила.
   Модель тоже отвечает строго `ATTACH_TO_GROUP` / `NEW_GROUP` / `NON_LEAD` —
   это по-прежнему автоматическое решение, просто принятое моделью, а не
   регулярным выражением.

`AMBIGUOUS` (то, что показывается на `/unassigned`) — это **осознанно** не
третий рабочий путь, а редкий отказ и первого, и второго механизма, когда
по ТЗ («никогда не угадывать») лучше спросить человека, чем молча слепить
два разных контакта в один или продублировать лид. Если система стабильно
уходит в `AMBIGUOUS` на обычных, не пограничных сообщениях — это сигнал, что
что-то в автоматике недонастроено, а не что ручной шаг — это норма.

**Что именно нашлось и исправлено в этой итерации.** В присланном логе
голосовое сообщение получило `AMBIGUOUS` с пояснением модели: *"similarity in
phone numbers"* — то есть LLM реально вызывался (`OPENAI_API_KEY` настроен
корректно), но не рискнул выбрать между двумя кандидатами с «почти
одинаковыми» номерами. Причина оказалась в детерминистическом слое: номера
сравнивались как сырые строки цифр, а один и тот же номер менеджеры
записывают по-разному — «+7 705 123 45 67» в одном сообщении и «8 705 123 45
67» в другом (расшифровка голосового). После извлечения цифр это `77051...`
и `87051...` — разные строки, хотя номер один и тот же, поэтому точное
совпадение (`exact_email_or_phone_match`) не срабатывало, и решение уходило
туда, где и должно быть после этого — к LLM, который справедливо не
угадывает. **Исправлено**: сравнение телефонов теперь ведётся по последним 10
значащим цифрам (`phone_match_keys()` в `grouping_worker.py`) — так «+7...» и
«8...» для одного и того же номера совпадают, а разные номера по-прежнему не
путаются. Проверено тестом: то же голосовое сообщение из лога теперь
автоматически, без единого обращения к LLM, приклеивается к правильному
лиду (`exact_email_or_phone_match`).

**Как ещё снизить частоту `AMBIGUOUS` на практике**, если после этого
исправления она всё ещё будет попадаться:

* Перед демонстрацией/новым раундом тестирования выполните
  `python grouping_worker.py --rebuild --once` — это очищает только
  производные `lead_groups`/`grouping_results`, накопленные за много
  предыдущих тестовых прогонов. Чем больше «открытых» тестовых групп с
  похожими тестовыми номерами одновременно видит правило/LLM, тем выше шанс
  ложной неоднозначности — это не баг, а следствие тестовых данных,
  накопившихся в базе.
* Проверьте `ACTIVE_GROUP_HOURS` (сейчас 12) — если тестовые сообщения шлются
  за пределами этого окна относительно друг друга не специально, можно
  временно уменьшить, чтобы старые тестовые группы переставали быть
  кандидатами.
* Подтвердите, что `OPENAI_API_KEY` задан в `.env`, который реально
  подхватывается процессом `grouping_worker.py` (судя по логу — задан).

## «status=synced, а лида в Bitrix не видно» — диагностика

Если в логе `lead_group_id=... status=synced bitrix_lead_id=35`, карточка в
Teams говорит «обновлён», а в CRM ничего нового нет — запустите:

```bash
python check_bitrix.py        # общая картина: режим CRM, все лиды, сколько сконвертировано
python check_bitrix.py 35     # подробно по конкретному лиду
```

Скрипт только читает портал и отвечает, где лид на самом деле. Три типовые
причины, все три теперь обрабатываются кодом:

* **Лид удалили в Bitrix вручную.** При тестировании это происходит постоянно.
  Раньше связка `external_key → bitrix_lead_id` оставалась навсегда: воркер
  вечно пытался обновить несуществующий лид и **никогда** не создавал его
  заново — контакт исчезал из CRM безвозвратно. Теперь удалённый лид
  распознаётся (`status=lead_missing_in_bitrix action=recreate`), связка
  очищается, лид создаётся заново.
* **Лид сконвертирован в сделку.** Если в портале включён простой режим CRM
  или на стадии лида стоит робот «создать сделку», лид сразу получает
  `STATUS_ID=CONVERTED`, пропадает из рабочего списка лидов, а сделка,
  созданная из него, при обновлении лида **не меняется**. Формально
  `crm.lead.update` отрабатывает успешно — в логе `status=synced`, в Teams
  «обновлён», а менеджер новых данных не видит нигде. Теперь это
  распознаётся (`status=lead_already_converted deal_id=...`), дубль лида не
  создаётся, а свежая выжимка дополнительно уходит в таймлайн сделки.
  Если по ТЗ нужны именно лиды — в портале: CRM → Настройки → Режим CRM →
  «Классический» (с лидами), плюс проверить роботов на стадии лида.
* **Смотрят не туда.** Раздел «Сделки» (`/crm/deal/kanban/`) и раздел «Лиды»
  (`/crm/lead/list/`) — это разные сущности. Лид с ID 35 открывается по
  прямой ссылке `/crm/lead/details/35/`.

Попутно убран лишний запрос: `crm.lead.get` при обновлении вызывался дважды
(второй раз — в `merge_existing_fields`, где результат даже не использовался).
При лимите портала в 2 запроса/сек это заметная экономия.

## Портал в простом режиме CRM (подтверждено диагностикой 21.09)

`python check_bitrix.py` на боевом портале показал:

```
Режим CRM портала: 2  (1 = классический с лидами, 2 = простой, без лидов)
Всего лидов через API: 12, из них созданы сервисом: 12, сконвертированы: 12
```

То есть сервис создаёт лиды корректно — **все 12**, у всех проставлен
`UF_CRM_TEAMS_GROUP_ID`. Но портал работает в простом режиме CRM, где лидов
нет как сущности: каждый созданный лид немедленно конвертируется в сделку и
получает `STATUS_ID=CONVERTED`. Поэтому в разделе «Лиды» пусто, всё видно в
«Сделках», а обновление лида не меняет уже созданную из него сделку.

Это настройка портала, а не дефект сервиса. ТЗ описывает работу именно с
лидами, поэтому для приёмки: **CRM → Настройки → Режим CRM → «Классический»**
(с лидами). После переключения новые контакты будут попадать в «Лиды» и
обновляться там же. Пока режим простой, сервис не молчит: он распознаёт
сконвертированный лид и дублирует свежую выжимку в таймлайн сделки
(см. раздел выше).

## Склейка разных контактов в один лид (исправлено)

На боевом прогоне в группу 14 попали два РАЗНЫХ человека: карточка лида
показывала «Роман Гуцаев — Альфа Групп», а в дословной расшифровке того же
лида лежало «Марат Маратович... оставил почту марат@gmail.com». Нашлись три
независимые причины, каждая закрыта:

* **Правило «части одного контакта рядом по времени» склеивало разные
  визитки.** Оно задумано под случай из ТЗ (голосовое + фото визитки одного
  человека без общего текста), но формально под него подходит и другой
  сценарий выставки: менеджер снял визитку посетителя A, через минуту —
  визитку посетителя B. Это прямо нарушало принцип самого ТЗ «близость по
  времени сама по себе никогда не достаточна: три контакта могут прийти за
  40 секунд». Теперь правило срабатывает только когда склеивать не с чем
  спутать: у нового сообщения нет собственных реквизитов и либо оно вовсе
  без читаемого текста, либо у группы ещё нет установленной личности.
* **Правило для коротких приписок срабатывало на визитках.** Фото визитки
  другого человека не содержит ни телефона, ни email, ни слов
  «подошёл/познакомился» — и подходило под правило «короткая приписка того же
  менеджера». Теперь припиской считается только то, что менеджер **набрал
  руками**: сообщение с вложением несёт собственную личность и разбирается
  по существу.
* **Группировка не знала, кого лид уже описывает.** `grouping_worker` смотрел
  только на реквизиты, вытащенные регулярками из сырого текста, и никогда не
  заглядывал в `lead_extractions`, где уже лежали проверенные ФИО и компания
  группы. Теперь личность группы (`already_extracted_contact`) передаётся и в
  правила, и в промпт модели, а в системный промпт добавлено прямое правило:
  если новое сообщение называет другого человека — это другой контакт,
  NEW_GROUP, а не присоединение.

Отдельно: **модель выдумывала обоснование склейки.** В логе LLM присоединила
голосовое к чужой группе с объяснением «The same normalized phone number
(87759196544)», хотя никакого номера в сообщении не было вовсе. Сервис принял
это на веру, потому что уверенность была выше порога 0.70. Теперь работает тот
же принцип, что и в извлечении полей: если модель ссылается на конкретный
телефон или email, он обязан реально присутствовать в сообщении — иначе
решение отклоняется (`llm_claimed_identifier_absent_in_message`).

## Потерянные email и приписки (исправлено)

Три независимых дефекта, найденные на прогоне 21.09:

* **Email, продиктованный голосом, не попадал в лид.** В расшифровке было
  «мэйл.самал.собачка.жмэйл.ком», в комментарии Bitrix этот текст лежал
  целиком — а поле Email у лида оставалось пустым: ни регулярка, ни модель не
  видят адрес без символа «@» и латиницы. Добавлен модуль
  `spoken_contacts.py`, который переводит продиктованный адрес в настоящий
  (`samal@gmail.com`): «собачка» → `@`, «точка» → `.`, «жмэйл/гмейл» →
  `gmail`, «ком/ру/кз» → зона, русские слова транслитерируются. Сама
  расшифровка остаётся дословной (этого требует ТЗ) — адрес добавляется
  рядом отдельной пометкой. Теперь он и попадает в лид, и участвует в
  сопоставлении контактов наравне с написанным текстом: голосовое и визитка
  одного человека связываются по email автоматически.
* **Email с фото визитки выбрасывался, если OCR его не прочитал.** Проверка
  требовала, чтобы адрес нашёлся регуляркой в ТЕКСТОВЫХ источниках. Но
  основной источник на выставке — само фото, которое читает vision-модель, а
  EasyOCR на CPU регулярно не дочитывает мелкий шрифт. В результате в лиде
  «Сергей Иванович Пименов — ЭНЕРГО» поле Email было пустым, хотя в
  аналитической выжимке того же лида стояло «Указан адрес электронной почты
  ghijkk@ghijk.ru». Теперь значение, подтверждённое ссылкой на изображение,
  засчитывается — сверять его текстом попросту не с чем. Порог уверенности
  для таких значений отдельный и намеренно выше обычного
  (`IMAGE_EVIDENCE_MIN_CONFIDENCE`, по умолчанию 0.90): ненадёжно прочитанный
  адрес в лид по-прежнему не попадает.
* **Приписки терялись, когда менеджер вёл несколько контактов.** Правила для
  сообщений того же менеджера срабатывали только если у него открыт РОВНО
  ОДИН контакт. На выставке это почти никогда не так, поэтому «Проект по
  экологии» и «Встреча в вт» не попали ни в один лид. Теперь берётся самый
  свежий контакт этого менеджера — но только если он заметно свежее
  предыдущего (`FOLLOW_UP_TIEBREAK_SECONDS`, по умолчанию 45 секунд). Если
  два контакта закрыты почти одновременно, выбирать действительно не из чего:
  сервис не гадает, и сообщение уходит на страницу «Без лида».

### Что сделано в этой итерации

* **Тип лида не определялся.** Лид 21: в расшифровке прямо «предложил
  предложение о партнерстве», в выжимке «предложил партнерство», а в поле Тип
  стоял Customer. Причина: тип брался ИСКЛЮЧИТЕЛЬНО из решения модели — если
  она сказала Customer, проверка партнёрских слов даже не запускалась. ТЗ
  формулирует правило как проверяемое условие («Partner допустим при явных
  словах партнёр/дистрибьютор/реселлер/интегратор»), а это можно установить
  детерминированно. Теперь, если такие слова дословно есть в тексте или
  расшифровке, тип поднимается до Partner с цитатой-основанием. Осторожность
  сохранена: расплывчатое «хотят сотрудничать» остаётся Customer, и слова,
  найденные только на фотографии, тип не поднимают — сверить цитату с
  картинкой построчно нельзя.
* **Проверка email на опечатки** (`email_hygiene.py`). Ловит три разные
  причины недоставки: кириллические буквы-двойники внутри латинского адреса
  (`gmаil.com` с русской «а» выглядит идентично и не доставится никогда),
  опечатку в домене по расстоянию редактирования (`gmail.con`, `yadnex.ru`) и
  отсутствие MX-записи у домена (опционально, `EMAIL_MX_CHECK`). Адрес **не
  правится молча** — ТЗ требует обратного: такой адрес остаётся пустым, а
  понятная причина видна в карточке лида. Корпоративные домены, которых нет
  в справочнике, ошибкой не считаются.
* **Видно, почему поле пустое.** Замечания валидации хранились всегда, но
  показывались кодами вида `emails[0]:invalid_or_absent_in_source`. Теперь
  рядом объяснение по-русски — это и есть ответ на вопрос «почему не прочитал
  email»: либо адрес не найден дословно в источнике, либо распознан
  неуверенно, либо прочитан по-разному в разных источниках.
* **Голосовые в шумном зале.** Добавлены: автоопределение языка с
  возможностью зафиксировать его (`WHISPER_LANGUAGE`), словарь выставки
  (`WHISPER_INITIAL_PROMPT` — без него «GITEX», «КП», «интегратор»
  распознаются как созвучный мусор), лесенка температур с отбраковкой
  зацикленного вывода (`compression_ratio_threshold`, `log_prob_threshold`) и
  порог тишины, чтобы шум зала не превращался в «факты».
* **Идемпотентность доказана, а не заявлена** (`test_idempotency.py`).
  Прогоняются все три способа из ТЗ и дополнительный сценарий `--rebuild`
  на временной базе с фальшивым порталом.
  Тест сразу нашёл реальный дефект: при догрузке за уже обработанный период
  старое сообщение приклеивалось к контакту, созданному ЧАСОМ ПОЗЖЕ него —
  потому что «ближайшая группа» искалась по полю `last_message_at`, где лежит
  самое позднее сообщение группы вообще. В живом потоке это не видно, на
  догрузке видно сразу. Исправлено: активность группы считается на момент
  разбираемого сообщения (`group_activity_before`).

### Про идею «искать контакт в интернете»

Автоматический поиск человека в открытых источниках сознательно не добавлен:
это персональные данные третьих лиц, собранные без их ведома и без правового
основания, а ТЗ такой задачи не ставит. Вместо догадки из интернета реализован
детерминированный ответ на ту же боль: проверка, доставится ли письмо
(опечатка, гомоглифы, наличие MX). Если обогащение из внешних источников всё
же понадобится, правильное место для него — отдельный воркер с явным
согласием и журналом источника по каждому полю, а не молчаливая подстановка в
лид.

## Что было исправлено/добавлено при проверке

Подробности и обоснование — в комментариях `ИСПРАВЛЕНО:` / `ДОБАВЛЕНО:` в
самом коде. Кратко:

* **Баг**: в `extraction_worker.py` email, распознанный на фото визитки или
  услышанный в голосовом (не встречающийся дословно в тексте Teams-сообщения),
  никогда не попадал в лид — код обращался к ещё не существующему на тот
  момент ключу и вызывал несуществующую функцию, поэтому цикл молча не
  делал ничего.
* **Баг**: `worker.py` не читал `ATTACHMENTS_DIRECTORY` из `.env` в отличие
  от `web_app.py` — при нестандартном пути вложения скачивались в одно
  место, а веб-интерфейс искал их в другом.
* **Улучшение**: `UF_CRM_TEAMS_MESSAGE_IDS` теперь отправляется в Bitrix в
  формате, который реально ожидает поле (список, если оно множественное, а
  не всегда JSON-строка) — определяется через `crm.lead.userfield.list`, как
  и для `UF_CRM_PRODUCT_INTEREST`.
* **Добавлено**: `templates/`, единый `static/styles.css`, `.env.example` — без них
  `web_app.py` не запускался (`TemplateNotFound` / `StaticFiles`
  "Directory does not exist").
* **Добавлено**: `web_app.py` теперь создаёт нужные ему таблицы при старте
  (если сервис поднимают до того, как отработал хоть один воркер), схемы
  таблиц дословно синхронизированы со схемами в соответствующих воркерах.
* **Добавлено**: страница `/admin` теперь позволяет администратору
  добавлять/отключать сопоставление "Teams-автор → сотрудник Bitrix" через
  форму, а не только через прямой SQL — без этого не было вообще никакого
  способа заполнить `employee_mappings` и не под кого назначить лид.
